# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Conilon Tech — a farm-management PWA for coffee (conilon/robusta) production: talhão (plot) mapping, adubação (fertilization) planning, pulverização (spraying), drench preventivo, equipe (labor/activity logging), estoque (inventory), pedidos (purchase orders), and a Gestão (management) reporting dashboard. Used daily in the field on phones by farm staff, and by the owner/admin for planning and purchasing decisions.

## Architecture

**No build step, no bundler, no package.json.** Each `*.html` file is a self-contained page: inline `<style>`, a single `<script type="module">` with the page's logic (the shared imports are `acesso.js`, see Permission model, and `menu.js`), Firebase v10.12.0 loaded from the `gstatic.com` CDN, Firestore `onSnapshot` listeners for real-time data, no client-side router. Navigation between pages is plain `<a href="other.html">`. There is nothing to install and nothing to compile — edit the HTML file directly and reload the browser.

Deployment is GitHub Pages, serving these files as-is from the repo root. There is no staging environment; merging to `main` is the deploy.

**Installable PWA**: `manifest.webmanifest` + `icones/` + `sw.js`. Every page's `<head>` carries the manifest/theme-color/apple-touch-icon tags and a one-line `serviceWorker.register('sw.js')`, just before the `style.css` link — copy them into any new page. `sw.js` is network-first (4 s timeout → cached copy) for the site's own files, so a deploy shows up on the next load; cache-first for pinned CDN libraries (`www.gstatic.com/firebasejs/`, unpkg, jsdelivr, cdnjs, sheetjs, Google Fonts); it never touches Firestore/Auth (offline data is Firestore's IndexedDB persistence). Bump `VERSAO` in `sw.js` when you change its precache list or strategy. The "📲 Instalar aplicativo" menu item comes from `beforeinstallprompt` in `menu.js` (Chrome/Android only; iPhone installs via Compartilhar → Adicionar à Tela de Início).

**Native shell (`app/`)**: a Capacitor project whose `server.url` is the published GitHub Pages site, so page changes reach the Android app with no rebuild. `.github/workflows/app-android.yml` builds the APK on pushes touching `app/` and, on `main`, uploads it to the `app-android` release (fixed download link). Signing uses `ANDROID_KEYSTORE_BASE64`/`ANDROID_KEYSTORE_PASSWORD` secrets when set, else the runner's debug key. iOS isn't generated yet (needs a paid Apple account). Inside the app `window.Capacitor` exists — `menu.js` uses it to hide "Instalar aplicativo". The app bundles `@capacitor/share` + `@capacitor/filesystem` so a page can write a generated file to the cache and open the native share sheet (used by `pedidos.html`'s PDF button: `window.print()` does nothing in the WebView and blob downloads are silently dropped, so in-app it generates the PDF with html2pdf and shares it). Pages reach these plugins via `window.Capacitor.registerPlugin('Share'|'Filesystem')` (they are not bundled into the page JS); adding a native plugin requires rebuilding/reinstalling the APK. Details in `app/README.md`.

### Firebase
Every page duplicates the same `firebaseConfig` object (project `talhoes-df836`) and the same auth bootstrap: `onAuthStateChanged` → redirect to `login.html` if unauthenticated → `getDoc(doc(db,'usuarios',uid))` to load the user's profile/permissions → render. There is one shared Firebase project — no multi-tenancy. All data (talhões, plans, inventory, orders, etc.) lives in one flat set of top-level Firestore collections: `talhoes`, `planosAdubacao`, `pulverizacoes`, `drenchPrevencao`, `equipeEmpregados`, `equipeMaquinas`, `equipeRegistros`, `estoque_produtos`, `estoque_movimentacoes`, `pedidos`, `recebimentos` (per-fazenda goods receipts; written by `recebimentos.html`), `usuarios`, `analises`, `amostras`, `recomendacoes`, `planejamentos_safra`, `catalogo_adubos`, `logs`, `irrigacaoSetores`, `irrigacaoRegistros`, `herbicidaRegistros`, `herbicidaConclusoes`, `configHerbicida`, `pluviometria`, `avaliacaoPlantas`, `avaliacaoRegistros`, `avaliacaoFotos`, `calibracoes`, `amostragemPontos`, `amostragemColetas`, `amostragemConfig`, `cadernoNotas`, `cadernoFotos`, `vazaoMedidores` (+ `dias` subcollection written by the ESP32s in `vazao/`, + `resumos` cached by the app), `vazaoConfig`, `vazaoAlertas`, `clima` (subcollections `dias`/`resumos`/`status`/`bruto` per station — written only by `clima/coletor.py`), `assistenteConversas`/`assistentePropostas` (Telegram assistant only, never read by the pages), plus legacy `registrosAtividade`/`talhoesAtividades` (from the removed `atividades.html`; nothing reads them now).

Visualizado em `clima.html`. Detalhes em `clima/README.md`. Regras: `clima/**` só leitura para logados; o app nunca escreve lá.

### Assistente no Telegram (`assistente/`, fora das páginas)
`assistente/` is a **Cloudflare Worker** (has its own `package.json`, as does `functions/`; deployed by `.github/workflows/assistente-deploy.yml`, which skips when `CLOUDFLARE_API_TOKEN` is unset). A Telegram bot that accepts **text or voice** and answers questions about any module and proposes **pulverização** schedules, **pedidos** and **recebimentos** (compra or transferência, same doc shape as `salvarRecebimento()` in `recebimentos.html`, gated like that page: `recebimentos` module + `fazendasModulo.recebimentos`, transferência also allowed via the origem fazenda). It works as a Claude tool-use loop (`src/index.js`) with these tools (`src/ferramentas.js`): `listar_talhoes`, `consultar` (generic Firestore query, falling back to client-side filtering when a composite index is missing), `ler_documento`, `propor_pulverizacao`, `propor_pedido`, `propor_recebimento`. The `propor_*` tools **never write**. They store the proposal in `assistentePropostas` and send a resumo with ✅/❌ inline buttons, and only the button callback writes. The written docs use the app's shape plus `origem:'telegram'`; the callback re-checks permissions. After a **pedido** is confirmed/written, the callback also generates a full PDF (resumo + distribuição por fazenda, built server-side with `pdf-lib` in `src/pdf.js` — Helvetica/Latin-1 only, no emoji) and sends it via Telegram `sendDocument` (`telegram.js` `enviarDocumento`), so it can be forwarded to the buyer; a PDF failure never undoes the already-written pedido. Firestore is accessed over REST with the same `FIREBASE_SERVICE_ACCOUNT` as the clima coletor. Permissions mirror the app: `nivelAcesso`/`fazendaPermitida` are copied, chats are mapped to app users via the `TELEGRAM_USUARIOS` secret (`{chatId: email}` → `usuarios` lookup by email), and readable collections are allowlisted in `COLECOES` (→ module key). **When adding a page/collection, register it in `COLECOES` and describe its fields in `src/prompt.js`, or the assistant can't see it.** `src/prompt.js` must stay static (prompt caching); date and user go in the user message. Conversation history (`assistenteConversas/{chatId}`) stores text only. Voice messages are transcribed by Workers AI Whisper (`src/audio.js`, binding `AI`, `language:'pt'`, talhão/fazenda names passed as `initial_prompt`). The transcript is echoed back to the user (🎤 «…») before Claude answers, and it reaches Claude flagged as voice so Claude asks when names or numbers look wrong. Setup guide: `assistente/README.md`.

### "Pendência" = atrasado (não o futuro)
System-wide rule: a **pendência** is something scheduled for a date/period that has **already passed and was not done** (planned date `< hoje`). Anything scheduled for a future date is **"programado"**, not a pendência, and must not be counted/flagged as an alert (a drench planned for October is not pending in July). Boundary: `data < hoje` (today is still within the deadline). This drives the Gestão **Geral** counters (`pulvPend`/`adubAtrasadas` via `calcAdubacoesAtrasadas` using `_dataPlanejadaAp`, not the old `mesAno`-string compare which was buggy/always-0; `drenchPend` = status≠realizado AND `data < hoje`), the 🗺️ mapa de atenção (red=atrasado=pendência, blue=programado/futuro, green=em-dia, grey=sem-dados — `_statusTalhoes` splits `overdue` vs `pend`/programado), and `index.html`'s **Pendências** section (only atrasados, grouped by fazenda → tipo; adubação collapsed to one item per talhão; estoque abaixo do mínimo also listed; respects `fazendasModulo` per module). Do **not** change the operational `status:'pendente'` field or the "Pendentes" list filters in `drench.html`/`pulverizacoes.html` — there "pendente" is the record's not-yet-done state (legitimately includes future), a different concept from the dashboards' pendência-as-alert.

### Permission model
**Shared rules live in `acesso.js`** (the only shared JS file, imported with `import { … } from './acesso.js'`): `nivelDoPerfil(perfil, mod)` (resolves the level, including the `_heranca` table below), `adminDoSistema(perfil)` (owner/system admin = `perfil==='admin'` or `modulos.admin==='admin'`, the same rule as `firestore.rules` — never "admin of any module", which was a real bug in Pedidos/Cotações) and `semAcessoAoModulo(perfil, mod)` (bootstrap gate). Pages keep thin local wrappers (`function nivelAcesso(mod) { return nivelDoPerfil(perfilAtual, mod); }`, `ehAdminSistema()`), plus their own `isAdmin()` and often `fazendaPermitida(fazenda)` / `podeConfirmar()` / `podeMarcar()`. `perfilAtual.modulos` (from the `usuarios` doc) maps module keys (`mapa`, `adubacao`, `pulverizacao`, `equipe`, `estoque`, `pedidos`, `gestao`, ...) to an access level (`'admin' | 'gerente' | 'encarregado' | 'operador' | 'nenhum'`). `perfilAtual.fazendasModulo?.[modulo]` optionally restricts a user to specific fazendas within a module. Server-side enforcement (`firestore.rules` v2, deployed by hand — Firebase console → Firestore → Regras, or `firebase deploy --only firestore:rules`): reads need an **active** account (`usuarios` doc exists and `ativo != false`); writes need `podeAbrir` on one of the modules that own the collection (`modulosDe()` table — a mirror of `HERANCA`/`ABERTOS` from `acesso.js` lives in the rules, keep them in sync); `usuarios` self-signup must be `ativo:false` with no admin/gerente levels (the owner activates it in Admin), only the owner updates/deletes users, writes `config`/`catalogo_adubos`, or deletes `logs`; `clima/**` and `assistente*` are never written by the app; `vazaoMedidores`/`vazaoAlertas`/`vazaoConfig` (read) stay open to any signed-in account because the ESP32 device account has no `usuarios` doc. Per-fazenda filtering is still client-side only (pages query whole collections). **When a page starts writing to a new collection, add it to `modulosDe()`** or only the owner can write it; run `testes/regras.test.mjs` (emulator; instructions in its header). When adding a new admin-only feature, follow the existing pattern: hide the button/tab and also guard the handler function itself (defense in depth), matching how `drench.html`'s Planejamento tab is gated.

**Every tool = one module key. When you add a new page/tool, register it in `admin.html` so the owner can grant access per-user and per-fazenda, otherwise it silently escapes admin control.** Concretely: (1) add `{id,label}` to `MODS` (the per-user access-level list) and `{id,label,ico}` to `MODS_LOCAL` (the per-fazenda modal) in `admin.html`; (2) gate the page bootstrap — redirect to `index.html` when `nivelAcesso('<key>')==='nenhum'` (or, for pages that existed before the gate or are open by default like `clima`, use `semAcessoAoModulo(perfilAtual,'<key>')`, which only redirects when the key is *explicitly* `'nenhum'`, so users whose profile simply lacks the key aren't locked out); (3) filter its fazenda-scoped content via `fazendaPermitida()`/`fazendasModulo?.['<key>']`; (4) add the item to `menu.js` with `acesso:'<key>'` (and to `ABERTOS` in `acesso.js` if the page gates with `semAcessoAoModulo`), plus a `--ico` entry in `style.css`. `salvarFazendasUsuario` in `admin.html` iterates over every module block actually rendered in the modal (`[id^="fmchips-"]`) — do NOT reintroduce a hardcoded module list there, or new modules' fazenda selections get dropped on save (this was a real bug). **Derived tools inherit a parent module for retrocompat**: `nivelAcesso` maps `drench→pulverizacao` and `cotacoes→pedidos` via its internal `_heranca` table, so a user who already had the parent keeps the derived tool until an admin sets the derived key explicitly. Add to `HERANCA` in `acesso.js` when a new tool should default to an existing module's audience.

### The sidebar menu lives in `menu.js`
The menu (sections, icon, label, href, required `acesso` module) is defined once in `menu.js`; every page except `login.html` imports it (`import { gerarMenu } from './menu.js'`) and calls `gerarMenu(perfilAtual)` after loading the profile. Add/reorder items there only. Visibility uses `podeAbrir(perfil, mod)` from `acesso.js`, which mirrors each page's own bootstrap gate: modules in its `ABERTOS` set (pages that predate the gate or have none — adubacao, pulverizacao, equipe, estoque, pedidos, cotacoes, gestao, clima, analises, recomendacoes, planejamento) are hidden only when explicitly `'nenhum'`; the rest need a level in the profile. **When a page's gate changes, update `ABERTOS` to match**, or the menu offers a page that bounces the user (or hides one they can open). The Admin item shows only for `adminDoSistema`, the same rule `admin.html` now gates on. `index.html`'s atalhos (`data-mod`) and its Clima/Pendências blocks use `podeAbrir` too. Canonical order: Dashboard → Mapa → Adubações → Pulverizações → Drench → Irrigação → Clima → Herbicida → Equipe → Estoque → Pedidos → Cotações → Calibração → Avaliações → Amostragem → Caderno de Campo, then (Análise) Gestão → Análises → Recomendações → Planejamento → Admin. The page itself still does finer-grained gating (e.g. `clima.html` filters stations by `fazendasModulo.clima`).

### `type="module"` inline-handler gotcha (recurring bug source)
Every page's script is `<script type="module">`, so top-level `let`/`const` state is module-scoped, not global. Inline HTML attributes like `onclick="minhaVar = ...">` run in the **global** scope and silently fail to touch module state (no error — the assignment just creates an unrelated global). This has caused real, hard-to-notice bugs in this codebase (e.g., a filter dropdown that visually looked selected but never actually filtered anything). The fix, used consistently across the app: never mutate module state directly from an inline attribute — always call a `window.xxx = function(...)` bridge that's explicitly assigned in the module script, e.g. `window.setDrFaz = function(v) { drenchFiltroFazenda = v; renderTab(); }`, and reference `onchange="setDrFaz(this.value)"` in the HTML. Grep `window.set[A-Z]` in any page for the existing convention before adding a new stateful filter/control.

### Retrocompat and derived/legacy data
Several collections carry data shapes that evolved over time; new code reads old and new shapes rather than migrating documents (e.g., `alvoPrevencao` may be a single string or an array; `pulverizacoes` docs use `dataRealizada` with fallback to `data`; adubação `aplicacoes` may lack per-product `feito` state on old Fertinox multi-product records — see `materializarProdutos()` in `adubacoes.html`). Follow this pattern — add fallback reads for older shapes rather than backfilling Firestore documents. **Adubação `mesAno` exists in two formats in the wild**: `"Julho/2026"` (nome/ano — what `adubacoes.html` writes) and `"2026-07"` (ISO — older/other-source docs). Planos also carry `mesIdx`/`ano` fields — but the ISO-format docs came from `planejamento.html`'s approval, which until Oct/2026 wrote `mesIdx` **1-12** ("2026-07" with `mesIdx:7`) and created a new doc on every approval. Always resolve month/year via `gestao.html`'s `_planoMesAno(plano)` (or `index.html`'s `planoMesAno`), which parse `mesAno` first and fall back to a 0-11 `mesIdx`; never compare `p.mesIdx` directly. Planejamento now writes `"Julho/2026"` + 0-based `mesIdx` and upserts into the existing plano of that talhão+mês (replacing its own not-yet-done aplicação on re-approval) — the old `filtrarPlanos` used a raw `mesAno + '-15'` string compare that silently excluded `"Julho/2026"` docs, which made the Gestão **Adubação tab** show 0 executados even with confirmed adubações. Note `adubacoes.html` itself still looks up planos by the exact `"Nome/Ano"` string, so ISO-format planos aren't findable/confirmable there until that's also made format-agnostic.


### Gestão (`gestao.html`) vs. per-module pages
`gestao.html` is a read-only, cross-module reporting surface (KPIs, PDF/Excel export via `xlsx.full.min.js`, filters). Tab-by-tab details (Geral, Nutrientes, Pulverizações, Adubação sub-views and their helpers) are in [`docs/paginas.md`](docs/paginas.md#gestaohtml). It has historically had zero Firestore writes; if you add a write there (e.g. a persisted filter/config), that's a new pattern for that file — consider whether the write belongs in the operational page instead (e.g. planning/scheduling config belongs in `drench.html`'s admin-only Planejamento tab, not in the Gestão report, per prior product decision).

### Consistent per-page details worth reusing rather than reinventing
- `formatarData(d)` (`YYYY-MM-DD` → `DD/MM/YYYY`), `sanitizar(str)` (basic HTML-escape), `corFazenda(nome)` — repeated near-verbatim in most pages.
- Leaflet 1.9.4 (unpkg CDN) for any map (`mapa.html`, `drench.html`, `pedidos.html`, ...), tile source `server.arcgisonline.com/.../World_Imagery`. Map instances bound to a container that gets wiped by `innerHTML` (as in report-style pages) must be destroyed and recreated on every render — see `renderDrenchCobMapa` pattern.
- Chart.js 4.4.0 (jsdelivr CDN) for dashboard/report charts.
- CSS custom properties (`--v`, `--ve`, `--vb`, `--c`, `--cb`, `--cl`, `--rad`, `--rs`, ...) are redefined per-file in `:root` with the same names/values — check what a given page already defines before introducing a new one.
- **Visual identity lives in `style.css`** (design system v3, the one shared stylesheet), linked as the **last** element of every page's `<head>` so its `:root` tokens and shell rules win over the inline `<style>`. It owns: the palette (remaps the legacy `--v`/`--ve`/... names), fonts (`--font-body` Inter, `--font-display` Archivo made semi-condensed by `body{font-stretch}`, `--font-mono` = Inter with tabular numbers — pages write `font-family:var(--font-*)`, never a font name; Chart.js options use `'Inter'`), the green topbar, the dark sidebar (fixed on ≥1100px), the shared `.tab`/`.ped-tab` bars, and the **vector menu icons**: `.menu-ico`/`.atalho-ico` hide the emoji from `gerarMenu()` and draw an SVG mask chosen by the link's `href` (`[href="x.html"]{--ico:…}` at the end of the file). A new page needs a `--ico` entry there, and must keep `<link rel="stylesheet" href="style.css">` right before `</head>`. Change look-and-feel there rather than page by page.
- Pages generally cap content width on wide viewports: `@media(min-width:600px){ .container { max-width:580px; margin:0 auto; } }` — apply this to any new page so it doesn't stretch full-bleed on tablet/desktop.

## Development workflow

No linter, no formatter, no build/CI pipeline. Small dependency-free tests live in `testes/` (`node testes/acesso.test.mjs`, `node testes/calibracao.test.mjs` — the latter extracts the real functions from `calibracao.html` and runs them against a fake `document`); run them when touching that code. Validate other JS changes by extracting the module script and running `node --check` on it (fast syntax check with no network/DOM), e.g.:
```bash
node -e "
const fs = require('fs');
const html = fs.readFileSync('drench.html','utf8');
const m = html.match(/<script type=\"module\">([\s\S]*?)<\/script>/);
fs.writeFileSync('/tmp/check.mjs', m[1]);
"
node --check /tmp/check.mjs
```
There's no way to run the app against real data without a live Firebase Auth login — there are no test/demo credentials available in this environment, so UI changes generally can't be visually verified end-to-end here. Note this limitation explicitly when reporting work rather than claiming visual verification that didn't happen.

Git remote is a local proxy; before pushing, `git fetch origin main && git rebase origin/main` (concurrent work lands on `main` frequently via other merged PRs) then `push --force-with-lease`.
